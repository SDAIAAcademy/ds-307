Two kinds of table

Facts record events at a grain; dimensions describe them

Facts

Trips, timepoint arrivals, taps, complaints. Many rows, numeric columns to aggregate, foreign keys to dimensions.

Dimensions

Routes, dates, vehicles, depots. Few rows, descriptive columns to group and filter by, one key each.

Ask of every column: do I add it up, or do I slice by it? The answer places it in a fact or in a dimension.

A quick exercise: call out columns and ask the room to say "fact" or "dimension": arr_delay_min (fact measure), depot (dimension), fare_type (an attribute of the tap kept on the fact, a degenerate dimension), route_name_ar (dimension).

The star

Four facts share dates, routes and vehicles

Facts are rectangles, dimensions rounded. Every line is many-to-one, from the fact to what it points at.

This is the star participants draw in Lab 2.1, task 3. Point out the two lines that go from a fact to another fact: taps and timepoints both point to trips. That makes trips a dimension of taps (one trip, many taps), which is how the semantic model treats it, and it is why the fan-out of Session 3 is possible.

Conformed dimensions

One date table and one route table serve every fact

Slowly changing dimensions

When a route changes, decide whether history changes with it

Type 1: overwrite

The new value replaces the old everywhere, past included. Right for corrections: a misspelt name.

Type 2: add a version

A new row with its own key and validity dates. Right for real changes: a longer route, a new depot.

The test. Would a January figure be wrong if it used the June value? Then it is type 2.

Other types exist (keeping a previous value in a column, separate history tables). Type 1 and type 2 cover most needs and are the two this course uses. FN-104 met the same idea as courier stints.

The as-of join

Join each fact row to the version valid on its date

SELECT t.*, r.route_key, r.route_name_en, r.length_km
FROM fct_trip t
JOIN dim_route r
  ON r.route_id = t.route_id
 AND t.service_date >= r.valid_from
 AND (r.valid_to IS NULL OR t.service_date <= r.valid_to)

85,010 trips in, 85,010 rows out. The open valid_to means "still valid".

Walk through the three conditions. Common errors: forgetting the IS NULL branch, which drops every trip of the current version; using BETWEEN with a NULL end. A warehouse often stores the surrogate key on the fact at load time instead; here the semantic model's dataset source does the as-of join, so the rule lives in one place.

A report that adds up wrong

Yasmeen's route report counts 334,786 taps in a month of 84,063

SELECT t.route_id, count(b.tap_id) AS taps,
       avg(CASE WHEN p.delay_min BETWEEN -1 AND 5 THEN 1.0 ELSE 0.0 END)
FROM fct_trip t
JOIN fct_boarding  b ON b.trip_id = t.trip_id
JOIN fct_timepoint p ON p.trip_id = t.trip_id
WHERE t.service_date BETWEEN ... GROUP BY t.route_id

From Lab 2.3. Ask the room to find the fault before the next slide. Nothing in the SQL is invalid; every join condition is right. The fault is that two "many" sides meet at one trip.

The fan trap

Joining two "many" sides through one row multiplies both

3.98 times. Every tap is repeated by the number of timepoints its trip reached: four, or two for a partial trip.

Row counts from Lab 2.3, task 2. Counting rows after each join is the fastest diagnosis there is. The general rule: a join is safe for a measure when it goes to the "one" side of that measure's fact.

The quieter error

The punctuality column is wrong too, and nothing looks odd

49.0%
R01 timepoint punctuality in the report
51.1%
R01 timepoint punctuality, computed alone

After the join each arrival is weighted by the taps of its trip: busy, late trips count more.

This is the chasm trap: two facts (taps, timepoints) related only through a shared dimension (trips). The tap total is obviously wrong; the punctuality is only slightly wrong, so nobody notices it. That is why reconciliation tests check totals, and why the model aggregates each fact separately.

The test that catches it

A reconciliation test compares the report with the source counted another way

def reconciles(df) -> bool:
    source = W.scalar(con, """SELECT count(*) FROM fct_boarding
                              WHERE service_date BETWEEN ... AND trip_id IS NOT NULL""")
    return int(df.taps.sum()) == int(source)
  • Write it first and watch it fail on the faulty report
  • Then fix the query, and watch it pass

A test that has never failed has not shown it can catch anything. This is the same habit as the toy test of Lab 1.3. In a pipeline these tests run on every load; dbt and similar tools call them data tests.

The fix

Aggregate each fact to the shared grain, then join

WITH taps  AS (SELECT t.route_id, count(*) AS taps
               FROM fct_boarding b JOIN fct_trip t USING (trip_id) ... GROUP BY 1),
     punct AS (SELECT t.route_id, avg(...) AS timepoint_on_time
               FROM fct_timepoint p JOIN fct_trip t USING (trip_id) ... GROUP BY 1)
SELECT route_id, taps, timepoint_on_time
FROM taps JOIN punct USING (route_id)

Each fact joins only "up" to trips, which is many-to-one; the two results meet at one row per route.

Point at the direction of each join: taps to trips, timepoints to trips, both many-to-one. The final join is one-to-one on route_id. This is exactly the shape of the SQL the semantic layer generates in Session 4.

The rule a model enforces

A semantic model joins only towards the "one" side

  • Every relationship is declared from the many side to the one side
  • A metric is aggregated in its own dataset, joining only along those arrows
  • A grouping that needs a "many" side is refused, not computed
  • Two metrics of two facts are aggregated apart, then joined on the dimensions asked for
requestboardings by timepoints.tp_seq
refusedno many-to-one path from boardings to timepoints: grouping would repeat rows

The refusal text is the real message of the course compiler, from the stretch of Lab 2.3. MetricFlow and Cube enforce the same idea with entities and join types. A refusal is a feature: it is the model saying "this question has no single answer at this grain".

The point of a semantic layer

Write each metric once; every tool asks for it by name

Without it

Each dashboard, notebook and agent writes its own SQL for "on-time rate". Three teams, three queries, three numbers.

With it

The model holds datasets, joins and metrics. A tool asks for on_time_rate by route type; the layer writes the SQL.

MetricFlowCube CoreApache Ossie files

Tool names are examples, not endorsements: MetricFlow (dbt Labs, Apache-2.0), Cube Core (Cube's open semantic layer), and Apache Ossie as the interchange format. This course writes the model as an Ossie document and compiles it with a small course module, so that it runs anywhere in a few seconds; the converters project translates Ossie to dbt MetricFlow, Cube and others. Sources: github.com/dbt-labs/metricflow, github.com/cube-js/cube, github.com/apache/ossie-converters.

An open specification

Apache Ossie is a vendor-neutral file format for semantic models

  • Formerly Open Semantic Interchange (OSI); renamed on entering the Apache Incubator in 2026
  • One YAML or JSON document per model: datasets, fields, relationships, metrics
  • A JSON Schema checks the document; converters move it between tools
  • The version in this course, 0.3.0.dev0, is still in development: re-check before each cohort

The project's announcement says the name changed and the specification did not. Its README lists converters for dbt, Cube, Snowflake, Polaris and others. Status is perishable: the catalog marks "the status of Apache Ossie" as a refresh item. Sources: ossie.apache.org/updates/ossie-enters-apache-incubator/ and github.com/apache/ossie, core-spec/spec.md (version history).

What the file holds

Datasets with fields, relationships from many to one, metrics

datasets:
  - name: trips
    source: SELECT t.*, r.route_key FROM fct_trip t LEFT JOIN dim_route r ON ...
    primary_key: [trip_id]
    fields:
      - {name: status, expression: {sql: status}, dimension: {}}
    metrics:
      - name: departed_trips
        expression: {sql: "SUM(CASE WHEN status <> 'cancelled' THEN 1 ELSE 0 END)"}
relationships:
  - {name: trips_to_routes, from: trips, to: routes, from_columns: [route_key], to_columns: [route_key]}

Point at three things: the dataset's source is the as-of join of Session 2, so the version rule lives once; a field is an expression over the source; a relationship goes from the many side to the one side. The full file has seven datasets and ten relationships.

Two places for a metric

Dataset metrics aggregate one dataset; model metrics combine them

Dataset-scoped

boardings.unique_cards: COUNT(DISTINCT card_id), bare field names of its own dataset.

Model-scoped

on_time_rate: AGG(trips.on_time_departures) / AGG(trips.departed_trips), each part aggregated first.

AGG() is the ratio of sums. The division happens after both parts are aggregated, so the layer cannot average ratios by mistake.

The specification allows a model-scoped metric to read a dataset metric only through AGG(dataset.metric). That rule is how Day 1's ratio-of-sums discipline is enforced by the file itself. Cross-fact ratios such as complaints per 10,000 taps use the same form, and the layer aggregates the two facts separately, as in Session 3.

What the interchange does not carry

Access rules ride in an extension that other tools may ignore

nonportable_extensions:
  - vendor_name: WADI_NOOR
    data:
      roles:
        network_analyst: {clearance: Public}
        east_depot_manager:
          clearance: Public
          row_filter: "routes.depot = 'East'"
  • Fields carry a classification: card_id and complaint_text are Restricted
  • A role may count a Restricted field, never group, filter or show it
  • Ossie defines no access rules: every consumer must enforce them again

The specification says plainly that non-portable extensions are vendor state Ossie carries and does not interpret. That is a design fact worth stating to a governance officer: moving a model between tools can silently drop its access rules. Access across many roles and areas is DS-408; here there are two roles. Source: Ossie core spec, "Non-portable Extensions".

Proving the model

25 test queries, each with a reference computed without the model

  • Each test is a request (metrics, dimensions, filters) and its expected rows
  • The expected rows come from independent SQL, written by hand, not from the layer
  • They cover ratios, distinct counts, Hijri months, the R07 versions, holidays and the October week
  • 25 of 25 is the evidence for the third course outcome

The reference queries live in labs/_tools/make_reference.py, written in plain SQL over the warehouse and never through wnt_semantic.py; participants receive only the expected rows in data/semantic/test_queries.yaml. A test whose reference was produced by the system under test proves only that the system agrees with itself. The capstone asks for the same on the fares area.

Where does the cancellation rate go?

You add cancellation_rate to the model. The trips dataset already has cancelled_trips and scheduled_trips. What do you write?

A dataset metric AVG(status = 'cancelled') on trips, used by every ratio
